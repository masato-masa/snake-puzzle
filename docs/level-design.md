# ステージ設計の指針

このゲームは**操作型パズル**（倉庫番・スライドパズルの系統）で、面白さは
「ルールの意外な帰結に気づくこと」に宿る。したがって、

> **ソルバーは検証に使う。生成には使わない。**

自動生成はあくまで候補出しで、採否は人が決める。実際、生成器が作った面は
ほぼすべて「置いただけの仕掛け」を含んでいた（監査で検出）。

---

## 1. 気づきの語彙

1 面につき、ここから**主となる気づきを 1 つ**割り当てる。
「この面は何を問うのか」を一文で言えないなら、それは面ではなく作業。

| # | 気づき | 由来 | 使う仕掛け |
|---|---|---|---|
| A | **止まる理由を先に作る** — 好きな場所で止まれない。止まれるのは何かにぶつかる時だけ | 制御の喪失 | 盤の端・障害物・砂・他のヘビ |
| B | **順番で行き先が変わる** — 同じ 2 手でも、順序が違えば別の形になる | 非対称性 | なし（基本ルールだけで成立） |
| C | **体は頭の軌跡をなぞる** — 曲がれば体も折れる。折れた形を狙って作る | 軌跡 | なし |
| D | **頭の位置が次の一手を決める** — 覆っているマスが同じでも、頭が左端か右端かで進める向きが違う | 不可視の状態 | なし（**見分けのつかない分岐**の材料） |
| E | **仲間は動く壁** — 先に片方を置いて、もう片方の止まる場所を作る | 前提条件 | 複数のヘビ |
| F | **押している間だけ開く** — ゲートを開けた側は、そこに残ることになる | 前提条件・不可逆性 | スイッチとゲート |
| G | **向きは保たれる** — 穴を抜けても入った向きのまま進み続ける | 制御の喪失 | ワープ穴 |

D が最も強い材料になる。盤を見ただけでは同じに見える 2 つの形が、頭の位置だけ違うために
片方からは解けて片方は詰む —— これが「そんな手があったか」の正体。
ただし**情報を隠してはいけない**。頭には目が描いてあり、注意して見れば必ず分かる。
つい見落とすところで止める。

### 気づきの組み合わせ

7 個の気づきに対して面数が多くなると、「1 面 1 気づき」だけでは同じ気づきの使い回しが
量産される（実測: E だけで 9 面、B だけで 6 面という偏りが発生したことがある）。
章 1（チュートリアル）は単体のままでよいが、**章 2 以降は 2 つ、終盤の卒業面は 3 つ**を
組み合わせることを基本にする。組み合わせは気づき同士が本当に噛み合っている必要がある
（例: F+E＝スイッチを仲間の体で押さえたまま、別のヘビが F のゲートを抜ける。
D+F＝頭の向きで、開いた 2 つのゲートのどちらを通れるかが変わる）。
ただの「同じ盤に 2 つ置いただけ」は組み合わせではない。

## 2. 1 面の作り方（逆算）

盤を先に作って「解けるか試す」方式は成立しない。全要素が噛み合う配置は偶然には出ない。

1. **問いを 1 つ選ぶ** — 上の表から。前の面の上に積めるか、章の中で重複していないかを見る。
2. **解の骨格を書く** — その気づきが必ず要る手順を、2〜6 手で書く。
   仕掛けを骨格に**含める**こと。「置いてから解けるか試す」と必ず飾りになる。
3. **終わりの形から巻き戻す** — ターゲット＝クリア時にヘビが占めるマスなので、
   終形を決めて「最後の一手の直前はどこにいたか」を逆にたどると、初期配置が出る。
   このとき、**止まる理由（壁・砂・仲間）を各手に 1 つずつ置いていく**。
4. **盤を切り詰める** — 使わない行・列を削る。遊休領域は「歩くだけの手」を増やし、
   検証も遅くする。「無駄が多い」と「検証が遅い」は同じ原因。
5. **監査にかける** — `npm test` が落ちたら直す。意図的に外すなら理由を書く（後述）。

### 実装上の制約: 同時に動かせる駒は 4〜5 匹まで

ソルバー（`solve`）は幅優先探索で全状態を展開する。仲間ヘビ・機構用ヘビを増やして
「気づきの組み合わせ」を作るとき、**独立して好きな順番で動かせる駒（ヘビ）が 6 匹を超えると
`maxStates: 400_000` の予算内で解が見つからなくなることがある**（実測: 6 匹は約 20〜30 秒で
通るが、7〜8 匹の構成は 200 万状態を展開しても解を発見できなかった）。特に、駒同士が
本当に順番依存（同じ移動でも先に動かした駒によって結果が変わる）だと状態数が急増するので、
4〜5 匹を目安にする。機構専用のヘビ（スイッチを踏むためだけの短いヘビ等）を足すときは、
その最終セルも必ずターゲットにする（`validateLevel` の「ヘビの長さ合計 = ターゲット数」は
例外なくハードエラーで、スイッチ／ゲートのマスをターゲットにすることも同様にハードエラー
なので、機構ヘビは「スイッチ／ゲートを踏む」ことと「実際のターゲットに乗る」ことを
同じ移動、または後続の移動で両立させる設計にする）。

## 3. 品質の物差し

`auditLevel()` が測る。指摘が 1 つでもあれば `npm test` が落ちる（警告ではなくエラー）。

| 指標 | 基準 | 意味 |
|---|---|---|
| 中身のある手 | 多いほど良い | 選択の余地があった手の数。手数の長さより信頼できる |
| 空手率 | **0.45 以下** | 最短手順のうち「選べる手が 1 つしかない」割合。高い＝盤が大きすぎる |
| 要素の必要性 | **飾りゼロ** | 抜いても同じ手数・同じ解の本数で解けるなら飾り。順番を強制する仕掛けは「解の本数が増える」ので検出されない |
| 連結性 | 分断なし | 壁で 2 つに割るのは「別のパズルを並べただけ」 |
| 遊休領域 | なし | 最短手順でも誤答でも一度も入らない行・列 |
| 退化解 | なし | 同じ向きの連打、複数匹いるのに 1 匹だけで解ける |
| 最短解の本数 | 1〜数通り | 多すぎると狙った気づきを回避される |

### 意図的な例外

基準を外したい面は、ステージ定義に**理由付きで**書く。黙って許すと、
意図した例外とただの不備が区別できなくなる。

```ts
audit: {
  reason: '上に 2 回で解けるのは意図どおり。穴を抜けて戻ってくることを見せる導入面。',
  allowDegenerate: true,
},
```

## 4. 落とし穴（実際に踏んだもの）

- **手数を難度の指標にする** → 盤を広げる圧力が生まれる。`中身のある手`で測る。
- **仕掛けが飾りになる** → 生成器が「配置」するだけで解き筋に組み込まないと必ず起きる。
  17 面中 9 面で発生していた。
- **チュートリアルから選択肢を奪う** → 合法手が 1 つしかない面は「間違えようがない」が、
  同時に何も教えない。もっともらしい誤答を必ず 1 つ用意する。
- **盤が中身に対して大きすぎる** → 遊休領域は手数を水増しし、探索も遅くする。

## 5. 高難度面の作り方（BFS 逆引き探索＋ソルバー検証）

「最短手数 2〜4 手は簡単すぎる」というフィードバックを受けて確立した手法。
`tangle-dense-7x7`（14 手・最短解 1 通り）と `tangle-dense-8x8`（16 手・最短解 4 通り）は
この手順で作った。手でターゲットを決め打ちする方式（第 2 節）は、
`coverAll`（「どのマスも“誰かが”乗っていればいい」＝どのヘビがどのマスを埋めるかは問わない）
の性質上、狙った手順と違う組み合わせで解かれる「近道」に何度も阻まれた
（的中率が低く、5 回中 4 回は近道が見つかって没にした）。この手法はその失敗から生まれた。

**「ソルバーは検証に使う。生成には使わない」という方針は変えていない** —
以下の探索は「配置から何が到達可能か」を機械的に列挙するだけで、どの気づき・どの初期配置で
挑むか（駒の配置、壁、ギミックの選択）と、出てきた候補のどれを採用するかは人が決める。
ソルバーは近道の有無と最短解の本数を数える検証役に徹する。

### 手順

1. **ターゲットなしで初期配置だけ決める** — ヘビの初期位置・壁・砂・ゲート/スイッチ・ワープ穴を
   ステージ案として組む（気づきの表から 1〜2 個を選んで骨格にするのはいつも通り）。
   このときはまだ `targets` を空にしておく。
2. **到達可能な全状態を BFS で列挙する** — `__tests__/tools/explore.test.ts` を一時的に作り、
   下記の骨格で「深さ・そこに至る手順・スネークの座標」を全状態について記録する。
   検証が終わったら必ず削除する（プロジェクトの一時ツールの慣習）。

   ```ts
   import {
     analyzeLevel, createGameState, legalMoves, move, stateKey, solve,
     type Level, type Pos, type Snake,
   } from '@/engine';

   // baseLevel = targets: [] の状態で、legalMoves/move を BFS で回し、
   // { snakes, depth, path } を状態ごとに記録する（重複は stateKey で弾く）。
   ```

   **注意**: `stateKey` はヘビの座標だけで状態を表す（ゲート開閉はスイッチ上の占有から、
   都度その場で再計算される値なので別途状態に持つ必要がない）。したがって
   ゲート・スイッチ・砂・ワープを使った盤でも、このBFSはそのまま使える
   （追加の状態管理は不要）。
3. **候補をふるいにかける** — 記録した状態のうち、
   - **深さ**が狙いの難度レンジに入っている（易しい導入面なら 4〜6 手、
     `tangle-dense-*` 級の高難度なら 12 手以上を目安に）
   - **穴の量**（`盤の外接矩形の面積 − 使われているマスの数`）が大きい
     ＝正方形・長方形にきれいに収まらない、いびつな形を優先する
     （単純な矩形は「2 匹を入れ替えれば同じ形になる」ような近道が起きやすい）
   - 初期配置がそのまま最終形になっている（＝すでにクリア済み）候補は除外する

   を満たすものだけ残す。
4. **候補ごとに `targets = その状態でのセル集合` で本物の `Level` を組み、`solve()` にかける** —
   `result.minMoves === 探索で記録した深さ` を確認する。**一致しなければ近道がある**ということなので
   その候補は捨てる（`coverAll` は「誰が」そのマスにいるかを問わないので、
   探索時に使った手順より短い経路で同じセル集合を埋められることがよくある）。
5. **近道のなかった候補を `analyzeLevel()` にかけ、`optimalPaths` の少ない順に並べる** —
   手数そのものより「最短解が何通りあるか」の方が難度の効き目が強い。
   `tangle-dense-7x7` は 1 通り、`tangle-dense-8x8` は 4 通りであり、
   ユーザー自身が「最短手数のパターンが 1 通りなのも難易度向上のポイント」と明言している。
6. **上位候補から形・見た目・気づきとの整合性を人が選ぶ** — BFS はあくまで「何が到達可能か」を
   見せるだけで、採用するかどうかは常に人の判断。
7. **`auditLevel()` で仕上げ確認** — 「使っていない壁」「盤の分断」が出たら、その壁を削って
   同じ深さ・同じ `optimalPaths` のままかを再確認してから外す
   （`tangle-dense-7x7` は当初 4 枚あった壁のうち 2 枚が装飾と判定され、除去して通した）。

### この手法とギミックの相性

最初の 2 例（`tangle-dense-7x7`, `tangle-dense-8x8`）は壁と複数ヘビ（気づき A・E）だけで作った。
その後、ゲート／スイッチ／砂／ワープを組み合わせた面（`quad-gate-sand-7x7` や
`gate-warp-sand-triad-7x7` など）も同じ手順でそのまま作れることを確認済み。
手順 2 の注記の通り `stateKey` はギミックの有無に関係なく状態を正しく捉えるので、
骨格に何を混ぜても手続きは変わらない。

### 「栓」テクニック — 3 匹以上の絡み合いで近道を防ぐ

3 匹以上のヘビだけで壁を使わずに（または壁を最小限にして）絡み合わせようとすると、
`coverAll` の性質上 BFS 探索が近道だらけになりやすい
（「2 匹の役目を入れ替えても同じセル集合になる」パターンが組み合わせ的に増えるため）。

対策: **絡み合わせたい 2 匹の最終形をまず決め、その最終セルのどれか 1 つに、
最初から動かない・体長 1 の「栓」用スネークを置いておく。**
栓が居座っているマスには他のヘビが入れないので、2 匹はその栓を避けて
決まった順番でしか自分の最終位置に収まれなくなり、近道が塞がれる。
`tangle-plug-6x7` / `tangle-plug-7x7` はこの技法で作った
（3 匹目 `c` が最初からターゲットの 1 つに乗ったまま、`a`・`b` が絡み合う）。
栓の置き場所を変えるだけで同じ骨格から難度違いの複数面が作れるのも利点。

## 6. 作業手順

```bash
npm run levels:audit     # 全ステージの品質監査（詳しい内訳つき）
npm run levels:report    # 難易度の内訳（分岐・読む量・一本道率など）
npm run levels:generate  # 候補の量産（採否は人が決める）
npm test                 # 監査・par・難易度・ソルバー再生をまとめて検証
```

新しいステージを足したら、`levels.ts` の `LEVELS` と `WORLDS` の両方に入れる
（`WORLDS` に入れ忘れると一覧に出ない。これもテストで検出する）。
