# ヘビパズル（snake-puzzle）

ヘビの頭を引っぱると、ぶつかるまで一気に滑る。体は通った経路を長さの分だけ覆う。
盤面の指定マス（ターゲット）をぴったり埋めるとクリア、というパズルゲーム。

Expo（React Native + TypeScript）製。Web・iOS・Android の同一コードで動く。

## 動かす

```bash
npm run web
```

ブラウザで http://localhost:8081 が開く。スマホ実機で試すときは `npm start` して Expo Go で QR を読む。

```bash
npm test
```

エンジンのユニットテストと、全ステージの検証（定義の健全性・解けること・最少手数・難易度）。

```bash
npm run levels:report
```

全ステージの難易度指標を表で出す。ステージを調整するときに使う。

```bash
npm run levels:generate
```

盤面をランダム生成し、狙った難易度帯に入ったものだけを JSON で出す。レシピは
`__tests__/tools/level-generator.test.ts` で編集する。

```bash
npm run typecheck
```

```bash
npm run shots
```

開発サーバーを起動した状態で、主要な画面を `screenshots/` に書き出す（端末の Chrome / Edge を使う）。
ルートやサイズを指定することもできる。

```bash
node tools/screenshot.mjs /game/trio-7x7 --size=390x844
```

## ルール

- 方向を指示すると、頭は **進めなくなるまで一気に滑る**。体は頭の通った経路を追従し、常に最新の N マスを占有する。
- 止まるのは、盤外・障害物・他のヘビ・**自分の体**の手前。移動判定には「移動開始時点の全身」を使う。
  この規則により、体のある向き（真後ろ）への操作は必ず 0 マスになる。
- 1 マスも動けない操作は無効（盤面も手数も変化しない）。
- ギミック:
  - **砂マス** … 乗るとその 1 マスで止まる。
  - **スイッチとゲート** … ヘビがスイッチに乗っている間だけ、同じ色のゲートが開く。開閉は移動開始時点で固定する。
  - **ワープ穴** … 入ると相方の穴から出て、同じ向きに進み続ける。出口がふさがっていたら入口で止まる。
- 全ターゲット（光るマス）がヘビで覆われたらクリア。
- 全ステージで **ヘビの長さ合計 = 光るマスの数**。つまりクリア＝はみ出さずぴったり覆うこと。
- ヘビが動ききってから、マスが点灯する演出 → クリア演出 → クリア画面、の順に出る。
- 移動アニメーションでは、胴体は**頭が通ったマスをそのままなぞる**（曲がり角を斜めに突っ切らない）。
  `move()` が返す `path` を UI に渡して実現している。

## 操作

操作方法は 3 つあり、どれでも同じように動かせる。

- **スワイプ**: ヘビの体のどこでもつまんで、動かしたい向きへ払う。
- **タップ**: 動かしたい方向のマスをタップする（選んでいるヘビの頭から見た向きへ進む）。ヘビをタップすると選択が切り替わる。
- **十字キー**: 盤面の下のボタン。中央の丸は、いま選んでいるヘビの色。

動けない向きに操作すると、ヘビがぷるんと縮んで知らせる。
- 「ヒント」を押すと、**いまの盤面**をソルバーに解かせて正解の 1 手を矢印で示す。詰んでいる場合はその旨を伝える。
- Web ではキーボードも使える: 矢印キーで移動、`Tab` でヘビを切り替え、`z` で 1 手戻す、`r` でやり直し、`h` でヒント。

## 章

- ステージは 3 つの章（くさはら / どうくつ / よぞら）に分かれ、章ごとに背景と登場するギミックが変わる。
  次の章は前の章を 6 割クリアすると開く（すでに遊んだ章は開いたまま）。

## 構成

```
src/
  engine/      ゲームロジック（純 TypeScript。React 非依存）
    types.ts   Pos / Dir / Snake / Level / GameState
    move.ts    滑る移動・クリア判定・Undo/Reset
    level.ts   ステージ定義の検証、探索用の状態キー
    solver.ts  幅優先探索。解の有無と最少手数を出す
    analyze.ts 難易度の測定。手数・分岐・正解の細さ・ミスの重さから★1〜5
    generate.ts ステージのランダム生成（必ず解ける盤面を作って難易度で選別）
  levels/
    levels.ts  ステージ定義（17 面）と章（WORLDS）
  components/  盤面・ヘビ・光るマス・ギミック・HUD・演出／プレイ画面本体（game-view）
  lib/         触覚フィードバックなどの小物
  app/         画面（expo-router）
    index.tsx            ステージ選択（章ごと）
    game/[levelId].tsx   プレイ画面
    editor.tsx           ステージエディタ（開発時のみ表示）
  storage/     クリア状況・自己ベスト（AsyncStorage）
```

ロジックが `src/engine` に閉じているので、UI・ソルバー・エディタ・テストはすべて同じ実装を共有する。

## 難易度のはかり方

`analyzeLevel()` は最短解の周辺（最少手数 + 2 手）だけを展開して、次の 4 つを測る。

| 指標 | 意味 |
|---|---|
| `minMoves` | 最少手数 |
| `branching` | 1 局面あたり選べる手の数。多いほど迷う |
| `optimalPaths` / `forcedRatio` | 正解手順の本数と、「正解が 1 手しかない」局面の割合 |
| `punishRate` | 正解から外れる手のうち、すぐ取り返せない割合 |

主軸は **`searchWork = minMoves × log2(branching)`**（＝プレイヤーが読む量）。
盤面の広さそのものではなくこれを使うのは、「広いだけで 3 手で終わる面」を難しいと誤判定しないため。
スコアを `starsFor()` で ★1〜5 に丸め、各ステージの `difficulty` として保存している。

## ステージの品質

```bash
npm run levels:audit
```

各ステージについて「置いた仕掛けが本当に働いているか」を機械で確かめる。
飾りになっている要素・盤の分断・使われていない行列・退化解などを名指しする。
指摘があると `npm test` が落ちる（警告ではなくエラー）。

設計の指針は [docs/level-design.md](docs/level-design.md)。1 面につき問いを 1 つ決め、
逆算で組み、監査にかける。

## ステージを追加する

手で作る場合:

1. 開発モードでステージ一覧の「ステージエディタ」を開く。
2. 盤面サイズを決め、光るマス・障害物・砂・ゲート・スイッチ・ワープ・ヘビ（頭から順にタップ）を配置する。
3. 「ソルバー実行」で解けること・最少手数・難易度★を確認する。
4. 出力された JSON を `src/levels/levels.ts` の `LEVELS` に追加する。

量産する場合:

1. `__tests__/tools/level-generator.test.ts` のレシピ（盤面サイズ・ヘビの長さ・ギミックの数・狙う★帯）を書く。
2. `npm run levels:generate` で候補 JSON を出し、実際に遊んで手触りの良いものを選ぶ。

どちらの場合も最後に `npm test`（定義の健全性・`parMoves`・`difficulty` の一致をチェック）。
